> 文档版本：1.0

> 项目版本：V2.5（Agent Tool Contract 基础设施补强）

---

## 1. V2.5 目标回顾

V2.5 的目标不是新增大模型能力，而是在 V3 接入 LLM 之前，把 Agent 的**安全工具层、动作计划、日志、确认机制和 Chat 承载能力**打稳。

核心原则：

1. Agent 不能直接改数据库，只能调用 Tool
2. Tool 内部只能通过 Service 修改数据
3. 危险操作必须确认
4. 所有 Agent 操作必须记录日志
5. Heartbeat 触发的执行反馈接入日志
6. 不引入真实 LLM，继续使用规则 IntentParser
7. 不新增 DB migration，充分利用 V2 已有 schema

同时修复 V2 遗留的三个已知限制：
- Heartbeat Done/Skip/Delay 操作不记录 ActionLog
- TimeBlockCard 菜单 Delay/Done/Skip 不含 Task 联动
- rejectAction 不写 action_log

## 2. 已完成内容

### V2.5.1 — Agent 类型契约补强

**文件**：`src/agent/types.ts`（全量重写）

新增类型（原有 `IntentType`、`ParsedIntent`、`ToolResult`、`ToolDefinition` 完全向后兼容）：

- **`AgentCommand`**：用户输入被 IntentParser 解析后的结构化命令（id / rawText / intent / params / createdAt）
- **`AgentActionPlan`**：Agent 准备执行的动作计划（commandId / toolName / params / requiresConfirmation / riskLevel / summary）
- **`AgentToolResult`**：ToolRouter normalize 后的统一工具结果，新增 `relatedTaskId`、`relatedTimeBlockId`、`requiresConfirmation`、`confirmationId`
- **`RiskLevel`**：`"safe" | "confirm" | "destructive"`（语义层风险等级，区别于 DB 的 `LegacyRiskLevel`）
- **`LegacyRiskLevel`**：`"low" | "medium" | "high"`，保留给 DB schema 持久化层使用
- **`CONFIRMATION_POLICY`**：声明式常量，明确每个 `IntentType` 的确认策略（delete_task / delete_time_block / reschedule_day → destructive；其余 → safe / confirm）
- **`toLegacyRiskLevel`**：`RiskLevel` → `LegacyRiskLevel` 转换工具函数
- **`ChatMessageMetadata`**：`conversation_messages.metadata_json` 的结构定义（intent / toolName / actionLogId / confirmationId / relatedTaskId / relatedTimeBlockId / resultType / source）

补全 `IntentType` 枚举（新增 5 个此前有 Tool 但无 Intent 的类型）：

| 新增 IntentType | 对应 Tool name |
|---|---|
| `list_time_blocks` | `list_time_blocks` |
| `bind_task_to_time_block` | `bind_task_to_time_block` |
| `detect_conflicts` | `detect_conflicts` |
| `get_free_slots` | `get_free_slots` |
| `explain_task` | `explain_task` |

命名约定：全部 snake_case，与 IntentParser 规则、`INTENT_TO_TOOL` 映射、ToolRouter 注册名三处完全一致。

### V2.5.2 — Tool Contract 和 ToolRouter 补强

**文件**：`src/agent/tools/BaseTool.ts`

17 个 Tool 文件均**未修改**，execute 签名保持不变，向后完全兼容。

### V2.5.3 — AgentService 重构（Command → Plan → Execute → Log）

**文件**：`src/agent/AgentService.ts`

`processInput` 重构为完整的 9 步链路：

```
用户输入
  ↓ IntentParser.parse → ParsedIntent
  ↓ 构造 AgentCommand { id, rawText, intent, params }
  ↓ ActionLogService.logRequest → pending log
  ↓ 意图未知 → logFailure，返回
  ↓ 查找 toolName（INTENT_TO_TOOL，新增 5 个映射）
  ↓ resolveArgs（"这个任务"引用解析 + 时间表达式解析）
  ↓ 构造 AgentActionPlan { commandId, toolName, params, riskLevel, summary }
  ↓ 需要确认 → ConfirmationService.create → logToolExecution → 返回 confirmationId
  ↓ 直接执行 → logToolExecution → ToolRouter.execute → logSuccess/logFailure
  ↓ 返回 AgentResponse { message, intent, toolResult, actionLogId, metadata }
```

`AgentResponse` 接口扩展：
- 新增 `actionLogId?: string`
- 新增 `metadata?: ChatMessageMetadata`

`confirmAction` 补强：
- 原版缺失 `logToolExecution` 调用，现已补全（logRequest → logToolExecution → logSuccess/logFailure）
- 返回值带完整 `metadata`

`rejectAction` 修复（V2 已知限制）：
- 原版不写任何 action_log
- 现在新建一条 cancelled 状态的 action_log，记录 confirmationId、原 toolName、原 args
- 不反查旧 log，避免 schema 无关联字段的依赖

### V2.5.4 — Heartbeat 操作接入 ActionLog

**文件**：`src/store/heartbeatStore.ts`

设计原则：**HeartbeatService 保持不变**（纯逻辑 + DB 操作），日志逻辑在 heartbeatStore 层注入。

实现：
- 模块顶层 `new ActionLogService()`（单例，不随 store action 重复创建）
- 新增 `logHeartbeatAction(action, block, success, errorMsg?)` 模块级辅助函数
- `startBlock` / `completeBlock` / `skipBlock` / `delayBlock` 四个 action 在执行后通过 `finally` 写入日志

日志格式：

| 字段 | 示例值 |
|---|---|
| `user_input` | `[heartbeat:complete_block] 写数据挖掘报告` |
| `detected_intent` | `heartbeat_complete_block` |
| `tool_name` | `heartbeat_complete_block` |
| `tool_args_json` | `{"blockId": "xxx", "taskId": "yyy"}` |
| `status` | `success` / `failed` |

注意：`heartbeat_*` 字符串**不进入 `IntentType` 枚举**，`IntentType` 仅表示 Chat Agent 用户意图。

获取 block 信息逻辑：优先从 store 运行时状态（`currentFocusBlock` / `pendingFeedbackBlock`）取，降级使用 blockId 字符串，日志写入失败不阻断主业务流程。

### V2.5.5 — TimeBlockCard Delay/Done/Skip 联动修复

**文件**：`src/store/timeBlockStore.ts`（新增联动 action）  
**文件**：`src/components/timeline/TimeBlockCard.tsx`（改为调用 store action）

V2 已知限制：TimeBlockCard 菜单的 Done/Skip/Delay 只调用 `updateBlockStatus`，无 Task 状态联动、无时间戳记录、无 ActionLog。

修复方案：**将联动能力下沉到 timeBlockStore**，组件不直接持有 service 引用。

`timeBlockStore` 新增三个 action（模块顶层 new `HeartbeatService` / `ActionLogService` 单例）：

```typescript
completeBlockWithLinkage(blockId: string): Promise<void>
skipBlockWithLinkage(blockId: string): Promise<void>
delayBlockWithLinkage(blockId: string): Promise<void>
```

每个 action 内部：
1. `heartbeatService.completeBlock/skipBlock/delayBlock` → 执行状态转换 + Task 联动（与 Heartbeat UI 路径完全一致）
2. 乐观更新 store 内 blocks 列表状态
3. `logTimelineAction` 写入 `timeline_*` 格式的 action_log

日志格式示例：

| 字段 | 示例值 |
|---|---|
| `user_input` | `[timeline:delay_block] 写报告` |
| `detected_intent` | `timeline_delay_block` |
| `tool_name` | `timeline_delay_block` |
| `tool_args_json` | `{"blockId": "xxx", "taskId": "yyy"}` |

`TimeBlockCard` 变更：
- `handleMarkDone` / `handleMarkSkipped` / `handleMarkDelayed` 改为调用 `completeBlockWithLinkage` / `skipBlockWithLinkage` / `delayBlockWithLinkage`
- 操作后额外调用 `loadTasks()` 刷新 Task 列表
- 移除 `updateBlockStatus` 的解构引用（tsc 无未使用变量警告）

## 3. 技术设计决策说明

| 决策 | 说明 |
|---|---|
| 不新增 DB migration | 现有 `agent_action_logs`（user_input / detected_intent / tool_name / tool_args_json / tool_result_json / status / error_message）和 `conversation_messages`（metadata_json）字段完全够用，V2.5 零 migration |
| Heartbeat 日志不进 IntentType | `heartbeat_*` 字符串作为普通 string 写入 `detected_intent`，不污染 Chat Agent 的 IntentType 枚举 |
| 联动能力下沉到 store，而非组件 | 避免 TimeBlockCard 每次 render 重复 new service；组件只调用 store action，符合 UI 层不承担业务逻辑的原则 |
| rejectAction 新建 log 而非反查 | DB schema 无 action_log → confirmation 的关联字段，新建 cancelled log 记录足够，不需改 schema |
| ToolRouter try/catch 统一容错 | 17 个 Tool 无需修改；BaseTool.requireParam throw 的错误由 ToolRouter 统一捕获转成 AgentToolResult |
| CONFIRMATION_POLICY 声明式策略 | 在代码层显式声明每个操作的风险等级，为 V3 接入 LLM 后的动态策略调整留好扩展点 |
| 17 个 Tool 文件均未修改 | 旧 execute 签名和返回类型不变，ToolRouter.normalizeResult 在路由层做适配，向后完全兼容 |

## 7. 已知限制（继承 + 新增）

1. **更改 Heartbeat 检查间隔需重开** — 继承自 V2，timer 创建时已固化间隔，修改后需关闭再开启 Heartbeat。
2. **没有桌面通知** — 继承自 V2，提醒仅在应用界面内展示，V3 可通过 Tauri notification 插件补充。
3. **多日 TimeBlock 不处理** — 继承自 V2，Heartbeat tick 只加载当日 TimeBlock。
4. **Delay 不自动重排** — V2.5 按设计仅记录状态，不新建 TimeBlock，V3 才做智能重排建议。
5. **IntentParser 覆盖率有限** — 新增的 5 个 IntentType（`list_time_blocks`、`bind_task_to_time_block`、`detect_conflicts`、`get_free_slots`、`explain_task`）已加入 `INTENT_TO_TOOL` 映射，但 `IntentParser` 的规则尚未覆盖这些 intent 的触发模式，用户需通过其他路径触发对应 Tool。V3 可补充规则或接入 LLM 理解。
6. **Heartbeat 日志 block 信息降级** — 若操作 blockId 既不在 `currentFocusBlock` 也不在 `pendingFeedbackBlock` 中（理论上不应发生），日志中的 title 会降级为 blockId 字符串。
