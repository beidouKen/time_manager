## 2. 今天完成到的程度

今天把 RAG 推进到了 **V3.8.1 RAG Knowledge Manager + Vector Prep**。

现在 RAG 已经不是纯 mock-first，而是：

```text
SQLite keyword RAG Foundation
  + seed_knowledge
  + Chat 主路径只读接入
  + Settings 维护期知识库管理器
  + draft / active / archived 生命周期
  + user_material 双门控
  + external_context 默认 draft
  + system_guidance / memory_summary UI 拒绝
```

但它仍然不是完整向量 RAG：

- 没有真实 embedding API。
- 没有 vector store。
- 没有 pgvector / sqlite-vec。
- 没有 hybrid retrieval / reranker。
- 没有 Coze 插件化 API。

因此版本命名仍保持在 V3.8.x，不进入 V3.9。

## 3. 核心实现清单

### 3.1 RAG 数据层

新增或扩展了 RAG 数据模型：

- `rag_documents`
- `rag_chunks`
- `status`
- `trust_level`
- `reviewed_at`

文档状态语义：

| 状态 | 含义 |
|---|---|
| `draft` | 草稿，默认不进入 Agent 检索 |
| `active` | 已启用，可以被默认 retrieve 召回 |
| `archived` | 已归档，不进入默认 retrieve |

可信度字段：

| 字段 | 当前用途 |
|---|---|
| `trust_level` | 展示和未来排序预留，当前不作为硬权限 |

### 3.2 RAG Service

`RagService` 现在承担真实 RAG 基础读写：

- `ingestDocument`
- `retrieve`
- `getDocument`
- `listDocuments`
- `deleteDocument`
- `activateDocument`
- `archiveDocument`
- `updateDocument`

关键收口：

- `ingestDocument` 使用事务包裹 document + chunks 写入。
- chunk 写入失败会 `ROLLBACK`，不留半成品文档。
- `retrieve` 默认只返回 `status='active'` 且未软删的文档。
- `sourceTypes` 是硬过滤。
- `tags` 只做排序加权，不做访问控制。

### 3.3 RAG Ingestion Policy

新增 `RagIngestionService`，把“资料怎么进入 RAG”从底层 CRUD 中分离出来。

它负责：

- `createDraftDocument`
- `activateDocument`
- `archiveDocument`
- `softDeleteDocument`
- `listDocuments`
- `getDocument`
- `updateDocumentMeta`
- `validateSourceTypePolicy`

Policy 结果：

| sourceType | UI 创建 | UI 激活 | 说明 |
|---|---|---|---|
| `seed_knowledge` | 允许 | 允许 | 内置知识，谨慎维护 |
| `user_material` | 允许 | 允许 | 用户/维护者录入资料 |
| `external_context` | 允许但强制 draft | 允许 | 外部资料不自动进入检索 |
| `memory_summary` | 拒绝 | 拒绝 | 留给未来 Memory 系统 |
| `system_guidance` | 拒绝 | 拒绝 | 仅系统内部维护 |

### 3.4 Chat 主路径接入

`chatStore` 注入了 `SqliteRagAdapter`。

默认检索：

```text
sourceTypes = ["seed_knowledge"]
```

当用户开启 Settings 里的 user_material 开关后：

```text
sourceTypes = ["seed_knowledge", "user_material"]
```

但 user_material 还必须满足：

```text
status = active
```

所以 Chat 侧形成双门控：

```text
全局 toggle ON
  AND
文档 status='active'
```

### 3.5 Recommendation 安全收口

今天还补齐了主路径建议的几个边界：

- 不再用 `currentDatetime` 当 RAG query。
- 改为用 `userInput + blockTitles` 这类语义信息构造 query。
- RAG 建议追加到用户可见回复前经过 `sanitizeRecommendation`。
- RAG 仍然不创建 confirmation。
- RAG 仍然不触发 ToolRouter。
- RAG 仍然不写 Task / TimeBlock。

### 3.6 Settings 维护期语料入口

新增 Settings 页面下的 RAG 区域：

- user_material 进入 Chat 的总开关。
- 知识库管理器入口。

知识库管理器是全屏 Dialog：

- 左侧文档列表、sourceType/status 筛选、搜索。
- 右侧详情、启用、归档、软删除。
- 新建资料表单。

收口后，管理器入口受 feature flag 控制：

```env
VITE_ENABLE_RAG_ADMIN=true
```

默认：

```env
VITE_ENABLE_RAG_ADMIN=false
```

也就是说，它现在更符合“维护期语料加入口”的定位：

```text
开发/维护期打开，
语料灌入和审核完成后封藏。
```

## 4. 今天明确下来的设计原则

### 4.1 RAG 不是业务数据库

业务数据库保存系统事实：

- tasks
- time_blocks
- schedules
- confirmations
- action_logs

RAG 保存参考资料：

- 时间管理理论
- 学习方法
- 课程材料
- 班级通知摘要
- 用户手动材料
- 未来 memory_summary

业务数据库决定“系统真实状态”；RAG 只提供“参考依据”。

### 4.2 RAG 不能直接执行

禁止路径：

```text
RAG -> ToolRouter
RAG -> tasks/time_blocks
RAG -> confirmation bypass
```

正确路径：

```text
RAG snippets
  -> Agent 参考
  -> 生成建议或计划草案
  -> PlanSafetyValidator
  -> ConfirmationPolicy
  -> ToolRouter
  -> Service
```

### 4.3 Knowledge Base 与 Memory Base 分区

今天明确把 RAG 概念拆成两个区：

**Knowledge Base**

- 人工录入、手动整理、外部导入的资料。
- 当前 V3.8.1 主要实现的是这个区。
- 它是 Agent 的资料室，只读参考。

**Memory Base**

- 用户行为长期总结。
- 未来由 Memory 系统生成。
- 当前只预留 `memory_summary` 类型，不开放 UI 写入。

分区原因：

- Knowledge 是资料。
- Memory 是用户习惯/画像。
- 二者来源、权限、过期策略、可信度不同。
- 避免外部资料污染用户记忆。
- 避免用户隐私被当成通用知识。

## 7. 当前版本的边界

这个版本可以被理解为：

```text
RAG v0.8
  = 真实 SQLite 知识库骨架
  + 可维护语料入口
  + Chat 只读接入
  + 生命周期治理
  + 安全边界收口
```

它还不是：

```text
RAG v1.0 / Vector RAG
```

因为尚未包含：

- EmbeddingProvider
- VectorStore
- HybridRetriever
- Reranker
- ReindexJob
- 多用户权限字段
- 外部平台 API / Coze 插件接口

## 8. 下一步建议

建议下一步保持克制：

1. 用 `VITE_ENABLE_RAG_ADMIN=true` 进行维护期语料录入。
2. 先维护少量高质量 `seed_knowledge / user_material`。
3. 不急于堆大量低质量资料。
4. 不急于进入 V3.9。
5. 等知识入口、资料状态、检索效果稳定后，再接：
   - EmbeddingProvider
   - VectorStore
   - Hybrid keyword + vector retrieve

一句话总结：

> 今天把 RAG 从“Agent 旁边的 mock 接口”推进到了“可维护、可检索、可封藏入口的本地知识库基础设施”。  
> 它已经能被 Agent 参考，但仍被安全壳限制为只读资料室。
