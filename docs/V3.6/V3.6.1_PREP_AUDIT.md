- `ConversationContextBuilder`：可保留，已接入主链路，负责 currentDatetime、timezone、recentMessages、短期操作记忆。
- `ResponseComposer`：可保留为统一出口雏形，但需要扩展 domain-level responses。
- `AgentTrace`：可保留，已写入 metadata，用于调试；但 UI 展示要降级为 dev-only。
- `refreshHints`：可保留，`chatStore` 已根据 hints 刷新 task/timeline。见 [chatStore.ts](</d:/Project_set/time_manager/src/store/chatStore.ts:73>)。
- `ToolRouter`：可保留，统一工具注册、执行、结果 normalize。
- Service / Repository 分层：可保留，`TaskService`、`TimeBlockService`、`ScheduleService` 边界清楚。
- `ConfirmationService` + `CONFIRMATION_POLICY`：可保留，但应迁入/包装成新的 `ConfirmationPolicy`。
- `get_free_slots` / `detect_conflicts`：可作为推荐排程基础能力保留。

## H. Risks

1. 全量回退风险：会丢掉 `ConversationContext`、`ResponseComposer`、`refreshHints`、`AgentTrace` 这些已经可用的骨架。
2. 继续补丁风险：每加一个测试句就多一个 if，最终 domain、semantic、response 混在一起，fallback 会越来越难收敛。
3. 只加 DomainRouter 风险：如果 TimeManagementAgent 内部仍直接写入、不推荐、不确认，用户体验只会“分流正确但处理粗糙”。
4. 提前接 RAG/Memory 风险：会掩盖当前边界问题，让错误路径更难定位。
5. 错误复用 TimeManagement pipeline 风险：把知识问答、写作、天气都送进 `SemanticFrameParser`，仍会变成 `unsupported_intent`。当前最大问题就在这里。
