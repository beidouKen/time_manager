## 四、关键设计决策

### 4.1 域路由优先级

```
assistant_meta > external_info > time_management > feedback_or_complaint
> writing_assistant > knowledge_qa > low_signal > general_chat（兜底）
```

规则均为正则/关键词匹配，无 LLM 调用，延迟可忽略。

### 4.2 LLMDirectHandler 只读硬约束

`general_chat / knowledge_qa / writing_assistant` handler：

- 构造时**不注入** `ToolRouter`、`TaskService`、`TimeBlockService`、`ScheduleService`。
- 即使将来接 LLM 也只取文本，丢弃 `toolName / params`，不调用 `router.execute`。
- `AgentHandlerResult` 此三类 domain 不携带 `refreshHints`（无写操作即无需刷新）。
- Gold test 断言：这三类 domain 处理后 `tasks.length` 和 `blocks.length` 保持为 0。

### 4.3 ActionPlanner 是决策器而非大脑

`ActionPlanner.create_and_schedule_task` 只输出意图分类：

| 输入特征 | 输出 kind |
|---|---|
| 有 `start_now`（从现在开始） | `tool`（直接 schedule_task） |
| 无明确开始时间 | `request_recommendation` |

`ActionPlanner` **不**计算 free slot、**不**生成推荐文案。推荐计算委托链为：

```
TimeManagementAgent（收到 request_recommendation）
  → RecommendationPlanner.plan()
    → AvailabilityProvider.getAvailability()   // 空闲窗口
    → SchedulingReasoner.rank()                 // 排序 + 理由
  → 取候选 [0] 写入 actionPlan.params.recommendation
  → composeRecommendationMessage()             // 生成文案
  → ResponseBoundary.finalize()                // 统一出口
```

后续接 `MemoryProvider` / `RagPlanProvider` 只需在 `TimeManagementAgent` 的调用链中注入，不污染 `ActionPlanner`。

### 4.4 ResponseBoundary 统一出口

所有用户可见消息的最终产出路径均为 `ResponseBoundary.finalize()`，该方法：

1. 优先使用 handler 已生成的 `message`（如 LLMDirectHandler 在线时的 LLM 回复）。
2. 否则按 `responseKind` 委托 `ResponseComposer` 生成预设文案。
3. 清除 JSON 包装（防止 LLM 输出 `{"message":"..."}` 被直接透传）。
4. 移除内部名（`userGoal`、`action`、`tool` 等关键词）。
