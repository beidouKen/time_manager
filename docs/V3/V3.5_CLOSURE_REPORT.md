# V3.5 Closure Report

## 1. 总体结论

- 是否建议封板：带条件封板。不建议作为无风险封板合入 V4 基线。
- 最大风险点：
  - `PlanProposal` 与 TimeBlock Tool 参数协议不一致：proposal 和 LLM prompt 使用 `timeBlockId`，但 `UpdateTimeBlockTool` / `DeleteTimeBlockTool` 实际读取 `blockId`。这会导致 Delay「今天做」和 End Feedback「延长当前任务」执行失败，也会影响 Chat LLM 对时间块更新/删除的主链路。证据：`src/agent/AgentService.ts:805`, `src/agent/AgentService.ts:833`, `src/agent/llm/prompts.ts:23`, `src/agent/tools/timeblock/updateTimeBlockTool.ts:21`。
  - `executePlanOption()` 只对 `update_time_block` 且同时存在 `start_time` + `end_time` 的情况做冲突检测，未覆盖所有写操作；End Feedback 延长只有 `end_time`，不会先检测冲突。证据：`src/agent/AgentService.ts:864`。
  - `executePlanOption()` 不写 `ActionLog`，也不写 ChatMessage metadata；Proposal 执行链路缺少审计闭环。证据：`src/agent/AgentService.ts:859`。
- 是否可以进入 V4：可以进入 V4 设计，但不建议进入 V4 功能开发基线；建议先修复 P0/P1 后再正式封板。

- Chat metadata：达标。LLM 响应 metadata 写入 `agentTrace`，chat store 会序列化到 `metadata_json`。证据：`src/agent/AgentService.ts:310`, `src/store/chatStore.ts:141`。

### V3.5-B: Delay / End Feedback Agent 化

- Delay 入口：部分达标。CurrentFocusCard 和 TimeBlockCard 不再在点击「延迟」时直接调用 `delayBlock`，而是打开 `DelayChoiceDialog`。证据：`src/components/heartbeat/CurrentFocusCard.tsx:43`, `src/components/timeline/TimeBlockCard.tsx:113`。
- DelayChoiceDialog：部分达标。提供「今天做 / 之后做」两个选择；「今天做」调用 `AgentService.proposeReschedule()` 并展示 `PlanProposalCard`；「之后做」仍直接调用原 `delayBlock` / `delayBlockWithLinkage` 逻辑，不经过 Agent proposal。证据：`src/components/heartbeat/DelayChoiceDialog.tsx:47`, `src/components/heartbeat/DelayChoiceDialog.tsx:61`, `src/components/heartbeat/DelayChoiceDialog.tsx:170`。
- 用户确认前写入：基本达标。「今天做」在用户选择 PlanOption 前不会写 TimeBlock；「之后做」在用户选择后才写 delayed 状态。
- Delay 执行硬伤：不达标。`proposeReschedule()` 生成 `timeBlockId`，但 Tool 需要 `blockId`，导致用户选择方案后执行失败。证据：`src/agent/AgentService.ts:805`, `src/agent/tools/timeblock/updateTimeBlockTool.ts:21`。
- Delay 重复渲染风险：存在。`CurrentFocusCard` 与每个 `TimeBlockCard` 都渲染 `DelayChoiceDialog`，且共用全局 `isDelayDialogOpen/delayTargetBlock`。同一个 block 同时出现在当前焦点和时间轴时，可能打开两个 Dialog 实例。证据：`src/components/heartbeat/CurrentFocusCard.tsx:125`, `src/components/timeline/TimeBlockCard.tsx:286`。
- End Feedback tick：达标。`tick()` 不再自动调用 `markEndPromptSent()`，仅使用内存 snooze 防抖。证据：`src/store/heartbeatStore.ts:184`。
- closeFeedbackDialog：达标。关闭弹窗只设置 `feedbackSnoozeUntil`，不写 DB 永久静默字段。证据：`src/store/heartbeatStore.ts:200`。
- End Feedback 选项：基本达标。支持「已完成 / 拆成剩余任务 / 延长当前任务 / 暂不处理」，另外提供「延迟安排」。证据：`src/components/heartbeat/ExecutionFeedbackDialog.tsx:198`, `src/components/heartbeat/ExecutionFeedbackDialog.tsx:207`, `src/components/heartbeat/ExecutionFeedbackDialog.tsx:216`, `src/components/heartbeat/ExecutionFeedbackDialog.tsx:233`。
- 拆分和延长 Agent 化：部分达标。两者都会调用 `AgentService.proposeEndFeedback()` 并用 `PlanProposalCard` 展示。证据：`src/components/heartbeat/ExecutionFeedbackDialog.tsx:82`, `src/components/heartbeat/ExecutionFeedbackDialog.tsx:95`, `src/components/heartbeat/ExecutionFeedbackDialog.tsx:255`。
- 延长冲突检测：不达标。延长 option 只有 `end_time`，`executePlanOption()` 的冲突检测条件要求同时有 `start_time` 和 `end_time`，因此延长不会先 detect_conflicts。证据：`src/agent/AgentService.ts:833`, `src/agent/AgentService.ts:864`。
- snooze 后再次提示：达标。关闭后 10 分钟内不弹，过期后下一次 tick 会重新从 DB 评估 pending feedback。证据：`src/store/heartbeatStore.ts:187`, `src/store/heartbeatStore.ts:203`。

## 3. 关键链路图

### Chat -> LLMPlanner -> Tool -> Service

```text
ChatInput
  -> chatStore.sendMessage()
     -> build recentMessages from existing messages only
     -> append current user message
     -> AgentService.processInput(userInput, { recentMessages })
        -> env guard: LLM disabled / API key missing => LLM error response
        -> processWithLLM()
           -> ContextBuilder.build()
           -> LLMPlanner.plan()
              -> DeepSeekClient.chat()
              -> parseLLMResponse()
              -> validate toolName / confirmation policy
           -> executeToolPlan()
              -> ToolRouter.execute(toolName, params)
                 -> Tool.execute()
                    -> Service / Repository
        -> assistant ChatMessage + metadata.agentTrace
```

### Delay -> Agent -> PlanProposal -> executePlanOption

```text
CurrentFocusCard / TimeBlockCard
  -> openDelayDialog(block)
  -> DelayChoiceDialog
     -> Today:
        AgentService.proposeReschedule(block)
          -> get_free_slots
          -> PlanProposal(options: update_time_block)
        PlanProposalCard
          -> AgentService.executePlanOption(option)
             -> detect_conflicts only if start_time + end_time
             -> update_time_block
     -> Later:
        onDelayLater(block.id)
          -> heartbeatStore.delayBlock() or timeBlockStore.delayBlockWithLinkage()
          -> HeartbeatService.delayBlock()
```

### End Feedback -> Agent -> PlanProposal / Tool

```text
heartbeatStore.tick()
  -> HeartbeatService.evaluateNow()
  -> pendingFeedbackBlock
  -> ExecutionFeedbackDialog
     -> Completed:
        heartbeatStore.completeBlock()
     -> Split:
        AgentService.proposeEndFeedback(block, "split")
        -> PlanProposal(create_task)
        -> executePlanOption()
        -> skipBlock() after successful create_task
     -> Extend:
        AgentService.proposeEndFeedback(block, "extend")
        -> PlanProposal(update_time_block end_time)
        -> executePlanOption()
     -> Dismiss:
        closeFeedbackDialog()
        -> in-memory snooze only
```

## 4. 风险点与建议

### P0

- 修复 TimeBlock Tool 参数协议：统一 `timeBlockId` / `blockId`。建议以 prompt、PlanProposal、Tool 入参、IntentParser resolver 为一个协议面整体修复，并补充最小集成测试。当前不修会导致时间块更新/删除类 LLM 操作和 Proposal 执行失败。
- 修复 `executePlanOption()` 的冲突检测策略。所有可能写入时间区间的操作都应先 `detect_conflicts`，包括 `create_time_block`、`schedule_task`、`update_time_block` 的 end-only 延长场景；延长需要先读取原 block 的 `start_time` 再检测。

### P1

- `executePlanOption()` 缺少 ActionLog / Chat metadata 审计记录。建议为 proposal_confirmed、tool_executed、error 写入 action log，至少记录 option、toolName、params、result。
- Proposal 执行缺少原子性。`schedule_task` 无 taskId 时会先 create task，再 schedule；若后续 schedule 失败会遗留任务。`ScheduleService.scheduleTaskToTimeBlock()` 也存在创建 block 后更新 task status 失败的部分成功风险。证据：`src/agent/tools/schedule/scheduleTaskTool.ts:54`, `src/services/ScheduleService.ts:74`, `src/services/ScheduleService.ts:84`。
- End Feedback split 存在状态不一致风险：`create_task` 成功后 `skipBlock()` 失败会被吞掉，用户仍看到成功并关闭弹窗。证据：`src/components/heartbeat/ExecutionFeedbackDialog.tsx:114`。
- Delay Dialog 可能重复渲染。建议将 `DelayChoiceDialog` 提升到单一顶层容器，例如 `HeartbeatPanel` 或 App-level portal，只渲染一个实例。

### P2

- `toAgentActionPlan()` 未接入且不是 `LLMPlanner` 方法。建议统一命名和导出方式，或删除未使用适配器，避免协议误解。
- LLM prompt 与部分 Tool 参数命名不一致不止 TimeBlock 更新：`bind_task_to_time_block` prompt 写 `timeBlockId`，Tool 实际按 `startTime/endTime` 重新排程，不是真正绑定已有 time block。建议 V4 前统一 Tool catalog。
- `processWithRules()` 虽已退出主链路，但仍保留完整 legacy 执行能力。建议后续加 dev-only guard 或拆到 legacy 文件，降低误接入风险。

## 5. 手工验收清单

- Chat：关闭 `VITE_LLM_AGENT_ENABLED` 后发送任意消息，应返回 LLM disabled 错误并显示 trace error。
- Chat：清空 `VITE_DEEPSEEK_API_KEY` 后发送任意消息，应返回 API key missing 错误并显示 trace error。
- Chat：发送创建任务、查询今日计划、删除任务三类输入，确认 metadata 中有 `agentTrace`，删除类必须进入确认。
- Chat：连续两轮对话，用第二轮指代「这个任务」，确认 recentMessages 不重复包含当前输入。
- Chat：尝试修改/删除时间块，验证 `timeBlockId/blockId` 修复后能真实执行。
- Delay：从 CurrentFocusCard 点击延迟，只出现一个 Dialog。
- Delay：从 TimeBlockCard 点击延迟，只出现一个 Dialog。
- Delay：「今天做」选择空闲时段后，应先检测冲突，再更新时间块。
- Delay：「之后做」选择后，应标记 delayed，并确认是否需要纳入 Agent proposal 审计。
- End Feedback：结束后弹窗，点关闭，10 分钟 snooze 后应再次提示。
- End Feedback：「拆成剩余任务」应创建剩余任务，并可靠地将原 block 移出待反馈队列。
- End Feedback：「延长当前任务」应先检测冲突；有冲突时不得写入。
- PlanProposal：人为制造冲突时，选择方案应提示冲突且不写 DB。
- PlanProposal：人为让后续写入失败，确认不会出现部分成功的脏状态。

## 7. 是否可以进入 V4

建议：暂不进入 V4 功能开发基线。先完成以下封板补丁后再进入 V4：

1. 统一 Tool 参数协议，特别是 `timeBlockId` / `blockId`。
2. 补齐 `executePlanOption()` 的冲突检测、审计记录和失败一致性处理。
3. 将 Delay Dialog 收敛为单实例，避免重复渲染。
4. 为 Delay「今天做」、End Feedback「延长」、End Feedback「拆分」补最小手工/自动回归用例。

完成以上后，可以带 V3.5 作为稳定基线进入 V4。
